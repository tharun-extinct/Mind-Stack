## 1. What Are JUnit 5 and Mockito?
 
| Tool | Role |
|---|---|
| **JUnit 5** | The test _runner_. Discovers test classes and methods, runs them, and reports pass/fail. |
| **Mockito** | The _mocking_ library. Creates fake stand-in objects for dependencies so the real implementations are never called during a test. |
 
Together they let you test a single class (e.g. `InventoryController`) in complete **isolation** — no Spring context, no database, no HTTP server.
 
---
 
## 2. The Three Core Annotations
 
Every controller test in this project starts with the same three-annotation pattern:
 
```java
@ExtendWith(MockitoExtension.class)   // (1) plug Mockito into JUnit 5
class InventoryControllerTest {
 
    @Mock                              // (2) create a fake dependency
    private InventoryService inventoryService;
 
    @InjectMocks                       // (3) create the real class and wire mocks into it
    private InventoryController inventoryController;
}
```
 
### `@ExtendWith(MockitoExtension.class)`
 
- Registers Mockito as a **JUnit 5 Extension**.
- Before every `@Test` method, Mockito scans the test class for `@Mock` and `@InjectMocks` fields and initialises them automatically.
- This replaces the older JUnit 4 `@RunWith(MockitoJUnitRunner.class)`.
- **No Spring context is started. No `@SpringBootTest` is needed.**
 
### `@Mock`
 
- Tells Mockito to generate a **proxy object** that implements the same interface/class as the field type.
- Every method on a mock returns a safe default by default (`null`, `0`, `false`, empty list).
- You can override those defaults with `when()` (see Section 4).
 
### `@InjectMocks`
 
- Tells Mockito to **instantiate the real class** (`InventoryController`) and inject all `@Mock` fields into it.
- Mockito first tries **constructor injection** (used here — `InventoryController` has a `@RequiredArgsConstructor` Lombok constructor).
- Falls back to setter injection, then field injection if no matching constructor is found.

## 3. How Mock Objects Are Created and Injected
 
### The real controller constructor (generated by Lombok)
 
```java
// InventoryController.java — Lombok generates this from @RequiredArgsConstructor
public InventoryController(
    InventoryService inventoryService,
    MessageService messageService,
    AuthService authService,
    UserRepository userRepository
) { ... }
```
 
### What Mockito does at test start-up
 
```
@ExtendWith triggers MockitoExtension
        │
        ▼
Scans InventoryControllerTest for @Mock fields
        │
        ├─► creates Mock<InventoryService>
        ├─► creates Mock<MessageService>
        ├─► creates Mock<AuthService>
        └─► creates Mock<UserRepository>
        │
        ▼
Finds @InjectMocks field (InventoryController)
        │
        ▼
Calls:  new InventoryController(
            mock_InventoryService,
            mock_MessageService,
            mock_AuthService,
            mock_UserRepository
        )
        │
        ▼
inventoryController is now a REAL object
but its internal fields point to MOCKS
```
 
The controller believes it has real dependencies. Every method call it makes on those dependencies is intercepted by Mockito.

## 4. Stubbing — Programming What Mocks Return
 
A mock that returns `null` for everything is not useful. **Stubbing** lets you pre-program specific responses.
 
### `when(...).thenReturn(...)` — happy path
 
```java
// From AdminControllerTest.java
PublishProductRequest request = new PublishProductRequest();
request.setSupplierProductId(1L);
request.setName("Oil");
request.setPrice(BigDecimal.valueOf(200));
request.setInitialStock(5);
 
when(adminService.publishProduct(request))
        .thenReturn(Product.builder().id(9L).name("Oil").build());
```
 
**Reading it in plain English:**  
> "When `adminService.publishProduct(request)` is called with exactly this request object, return a fake `Product` with id=9 and name='Oil'."
 
When the test later calls `adminController.publishProduct(request)`, the controller internally calls `adminService.publishProduct(request)`. Mockito intercepts that call and **returns the fake product** — no real service logic runs.
 
### Stubbing with specific argument values
 
```java
// From InventoryControllerTest.java
when(inventoryService.confirmReceipt(3L, "General Warehouse"))
        .thenThrow(new RuntimeException("error"));
```
 
This stub only fires when _exactly_ `(3L, "General Warehouse")` is passed. Any other arguments would fall through to Mockito's default (returning `null`).

## 5. Step-by-Step Data Flow Through an API Test
 
Using `AdminControllerTest.publishProduct_returnsOk_whenSuccess()` as a walkthrough:
 
### The test
 
```java
@Test
void publishProduct_returnsOk_whenSuccess() {
    // ── ARRANGE ──────────────────────────────────────────────────────────
    PublishProductRequest request = new PublishProductRequest();
    request.setSupplierProductId(1L);
    request.setName("Oil");
    request.setPrice(BigDecimal.valueOf(200));
    request.setInitialStock(5);
 
    when(adminService.publishProduct(request))
            .thenReturn(Product.builder().id(9L).name("Oil").build());
 
    // ── ACT ──────────────────────────────────────────────────────────────
    ResponseEntity<ApiResponse<?>> response = adminController.publishProduct(request);
 
    // ── ASSERT ───────────────────────────────────────────────────────────
    assertEquals(HttpStatus.OK, response.getStatusCode());
}
```
 
### Flow diagram
 
```
Test method
    │
    │  1. Build a real PublishProductRequest object (test data)
    │
    │  2. Register stub: when publishProduct(request) → return fake Product
    │
    │  3. Call adminController.publishProduct(request)   ← REAL method runs
    │         │
    │         │  Inside AdminController.publishProduct():
    │         │
    │         │  adminService.publishProduct(request)
    │         │        │
    │         │        └── Mockito intercepts → returns Product{id=9, name="Oil"}
    │         │
    │         │  return ResponseEntity.ok(
    │         │      ApiResponse.success("Product published", product)
    │         │  )
    │         │
    │  4. ResponseEntity<ApiResponse<?>> returned to test
    │
    │  5. assertEquals(HttpStatus.OK, response.getStatusCode())  ✓
    │
   PASS
```
 
### The `ApiResponse<T>` wrapper
 
Every endpoint in this project wraps its payload in `ApiResponse<T>`:
 
```java
public class ApiResponse<T> {
    private boolean success;   // true = ok, false = error
    private String message;    // e.g. "Product published"
    private T data;            // the actual payload
 
    // Static factory methods:
    public static <T> ApiResponse<T> success(String message, T data) { ... }
    public static <T> ApiResponse<T> error(String message) { ... }
}
```
 
The test receives a `ResponseEntity<ApiResponse<?>>`. It can assert on:
- `response.getStatusCode()` — the HTTP status (200, 201, 400, 403…)
- `response.getBody().getMessage()` — the message string
- `response.getBody().getData()` — the payload object
- `response.getBody().isSuccess()` — the boolean flag

## 6. Testing Error Paths with `thenThrow()`
 
The most important test in `InventoryControllerTest` verifies that when the service **throws**, the controller catches the exception and returns `400 BAD_REQUEST` instead of letting the exception propagate.
 
```java
@Test
void confirmReceipt_returnsBadRequest_whenServiceThrows() {
 
    // Stub the service to simulate a failure
    when(inventoryService.confirmReceipt(3L, "General Warehouse"))
            .thenThrow(new RuntimeException("error"));
 
    // Call the real controller method
    ResponseEntity<ApiResponse<?>> response =
            inventoryController.confirmReceipt(3L, "General Warehouse");
 
    // Verify the controller handled the error correctly
    assertEquals(HttpStatus.BAD_REQUEST, response.getStatusCode());
}
```
 
### Why this works — the controller's try/catch
 
```java
// InventoryController.java
@PostMapping("/supplier-products/{id}/confirm-receipt")
public ResponseEntity<ApiResponse<?>> confirmReceipt(
        @PathVariable Long id,
        @RequestParam(defaultValue = "General Warehouse") String location) {
    try {
        return ResponseEntity.ok(
            ApiResponse.success("Receipt confirmed", inventoryService.confirmReceipt(id, location))
        );
    } catch (RuntimeException e) {                          // ← catches the mock exception
        return ResponseEntity.badRequest()
               .body(ApiResponse.error(e.getMessage()));   // ← returns 400
    }
}
```
 
```
thenThrow(new RuntimeException("error"))
        │
        ▼
inventoryService.confirmReceipt(3L, "General Warehouse")
        │
        ▼  exception thrown
catch (RuntimeException e)
        │
        ▼
ResponseEntity.badRequest().body(ApiResponse.error("error"))
        │
        ▼
assertEquals(HttpStatus.BAD_REQUEST, ...)  ✓
```
 
The same `thenThrow` pattern is used in:
- `DeliveryControllerTest` — `markDelivered_returnsBadRequest_whenServiceThrows()`
- `InventoryControllerTest` — `confirmReceipt_returnsBadRequest_whenServiceThrows()`

## 7. Assertions — Verifying the Result
 
All assertions use **JUnit 5's `Assertions.assertEquals`** (statically imported):
 
```java
import static org.junit.jupiter.api.Assertions.assertEquals;
```
 
### Asserting HTTP status code
 
```java
assertEquals(HttpStatus.OK, response.getStatusCode());
assertEquals(HttpStatus.BAD_REQUEST, response.getStatusCode());
assertEquals(HttpStatus.CREATED, response.getStatusCode());
assertEquals(HttpStatus.FORBIDDEN, response.getStatusCode());
assertEquals(HttpStatus.UNAUTHORIZED, response.getStatusCode());
```
 
### Asserting response body message
 
```java
// From AuthControllerTest.java
assertEquals("Login successful", response.getBody().getMessage());
```
 
### How `assertEquals` works
 
```
assertEquals(expected, actual)
       │              │
       │              └── value produced by the code under test
       └── value you specified in the test
 
If expected == actual  →  test PASSES
If expected != actual  →  test FAILS with:
    "expected: <200 OK> but was: <400 BAD_REQUEST>"
```

## 8. Verifying Behaviour with `verify()`
 
`assertEquals` checks **what was returned**. `verify()` checks **what was called**.
 
```java
// From ProductControllerTest.java
@Test
void getAllProducts_usesSearch_whenKeywordPresent() {
    when(productService.searchProducts("milk"))
            .thenReturn(List.of(Product.builder().id(1L).name("Milk").build()));
 
    ResponseEntity<ApiResponse<?>> response = productController.getAllProducts("milk");
 
    assertEquals(HttpStatus.OK, response.getStatusCode());
    verify(productService).searchProducts("milk");   // ← behaviour assertion
}
```
 
`verify(productService).searchProducts("milk")` confirms that `searchProducts("milk")` was called **exactly once** during the test. If the controller called `getAllProducts()` instead, or didn't call the service at all, the test would fail.
 
### When to use `verify()` vs `assertEquals`
 
| Scenario | Use |
|---|---|
| Check the HTTP status returned | `assertEquals` |
| Check the response body content | `assertEquals` |
| Check that a service method was invoked | `verify()` |
| Check that a void method (e.g. send notification) was called | `verify()` |
| Check a method was never called | `verify(mock, never()).method(...)` |

## 9. Mocking Authentication / Security Context
 
Several controllers require a Spring Security `Authentication` object to identify the logged-in user. Since no Spring context runs in these tests, authentication must be mocked.
 
### Pattern A — inline `mock()` for simple controllers
 
Used in `CustomerControllerTest` and `SupplierControllerTest`:
 
```java
Authentication auth = mock(Authentication.class);
when(auth.getName()).thenReturn("c@example.com");
```
 
`mock(Authentication.class)` is a static Mockito method — it creates an anonymous mock on the spot without needing an `@Mock` field. Then `auth.getName()` is stubbed to return a known email string.
 
The controller calls `auth.getName()` internally to look up the user:
 
```java
// CustomerController.java (internal helper)
private User getCurrentUser(Authentication auth) {
    return authService.getCurrentUser(auth.getName());
}
```
 
So the test stubs the entire chain:
 
```java
when(auth.getName()).thenReturn("c@example.com");
User customer = User.builder().id(1L).email("c@example.com").role(Role.CUSTOMER).build();
when(authService.getCurrentUser("c@example.com")).thenReturn(customer);
```
 
```
auth.getName()  →  "c@example.com"
                        │
authService.getCurrentUser("c@example.com")  →  User{id=1, role=CUSTOMER}
                        │
controller proceeds with the fake User object
```
 
### Pattern B — real `UsernamePasswordAuthenticationToken` for auth flow tests
 
Used in `AuthControllerTest` to simulate a successful login:
 
```java
Authentication auth = new UsernamePasswordAuthenticationToken(
    "john@example.com", "x",
    List.of(new SimpleGrantedAuthority("ROLE_ADMIN"))
);
when(authenticationManager.authenticate(any())).thenReturn(auth);
```
 
Here, a real `Authentication` implementation is returned by the mocked `authenticationManager`. This tests the exact data the controller extracts after authentication succeeds.

## 10. Argument Matchers — `any()`
 
When you don't know or don't care exactly what argument will be passed to a mock method, use **argument matchers**:
 
```java
import static org.mockito.ArgumentMatchers.any;
 
when(authenticationManager.authenticate(any())).thenReturn(auth);
```
 
`any()` matches **any object** passed to `authenticate()`. This is necessary because the controller constructs the `UsernamePasswordAuthenticationToken` internally — the test cannot reproduce the exact object.
 
### Common matchers
 
| Matcher | Matches |
|---|---|
| `any()` | Any object (including null) |
| `any(SomeClass.class)` | Any instance of a specific type |
| `anyLong()` | Any `long` or `Long` value |
| `anyString()` | Any `String` value |
| `eq(value)` | Exactly the specified value (default when you pass a literal) |
 
> **Rule:** If you use _any_ matcher in a method call, _all_ arguments in that call must also use matchers. You cannot mix literals and matchers in the same `when()`.

## 11. Authorization Boundary Testing
 
`SupplierControllerTest` demonstrates testing **security boundaries** without a security filter chain:
 
```java
@Test
void viewInvoice_returnsForbidden_whenPaymentBelongsToAnotherSupplier() {
    Authentication auth = mock(Authentication.class);
    when(auth.getName()).thenReturn("sup@example.com");
 
    // Logged-in supplier has id=1
    User loggedInSupplier = User.builder().id(1L).role(Role.SUPPLIER).build();
    // But the payment belongs to a different supplier (id=2)
    User otherSupplier    = User.builder().id(2L).role(Role.SUPPLIER).build();
    SupplierPayment payment = SupplierPayment.builder().id(9L).supplier(otherSupplier).build();
 
    when(authService.getCurrentUser("sup@example.com")).thenReturn(loggedInSupplier);
    when(supplierService.getPaymentById(9L)).thenReturn(payment);
 
    ResponseEntity<ApiResponse<?>> response = supplierController.viewInvoice(9L, auth);
 
    assertEquals(HttpStatus.FORBIDDEN, response.getStatusCode());
}
```
 
### How the authorization check works
 
```
loggedInSupplier.getId()  →  1L
payment.getSupplier().getId()  →  2L
 
1L != 2L  →  controller returns 403 FORBIDDEN
```
 
The test proves the controller enforces ownership checks. No real Spring Security annotations are involved — the logic lives directly in the controller method, so the unit test can reach it.

## 12. Test Method Naming Convention
 
All test methods follow the **BDD-style three-part naming pattern**:
 
```
methodUnderTest_expectedOutcome_givenCondition
```
 
| Part | Meaning | Example |
|---|---|---|
| `methodUnderTest` | The controller method being tested | `confirmReceipt` |
| `expectedOutcome` | What the test expects to happen | `returnsBadRequest` |
| `givenCondition` | The scenario that triggers it | `whenServiceThrows` |
 
### Examples from this project
 
| Test name | What it tests |
|---|---|
| `confirmReceipt_returnsBadRequest_whenServiceThrows` | Error path in `confirmReceipt` |
| `publishProduct_returnsOk_whenSuccess` | Happy path in `publishProduct` |
| `login_returnsOk_whenCredentialsValid` | Successful login |
| `login_returnsUnauthorized_whenCredentialsInvalid` | Bad password |
| `placeOrder_returnsCreated_whenSuccess` | Order creation |
| `markDelivered_returnsBadRequest_whenServiceThrows` | Delivery error path |
| `viewInvoice_returnsForbidden_whenPaymentBelongsToAnotherSupplier` | Authorization boundary |
| `getAllProducts_usesSearch_whenKeywordPresent` | Branching / delegation logic |
 
This naming convention means test failure reports are **self-documenting** — you can read the test name alone and understand exactly what broke.

## 13. Full Annotated Examples
 
### Example A — `InventoryControllerTest` (error path, no auth)
 
```java
@ExtendWith(MockitoExtension.class)           // [1] Activate Mockito extension
class InventoryControllerTest {
 
    @Mock private InventoryService inventoryService;   // [2] Fake service
    @Mock private MessageService messageService;
    @Mock private AuthService authService;
    @Mock private UserRepository userRepository;
 
    @InjectMocks                               // [3] Real controller, mocks injected
    private InventoryController inventoryController;
 
    @Test                                      // [4] JUnit 5 discovers this method
    void confirmReceipt_returnsBadRequest_whenServiceThrows() {
 
        // [5] ARRANGE — program the mock to throw
        when(inventoryService.confirmReceipt(3L, "General Warehouse"))
                .thenThrow(new RuntimeException("error"));
 
        // [6] ACT — call the real controller method directly (no HTTP, no server)
        ResponseEntity<ApiResponse<?>> response =
                inventoryController.confirmReceipt(3L, "General Warehouse");
 
        // [7] ASSERT — verify the controller handled the error correctly
        assertEquals(HttpStatus.BAD_REQUEST, response.getStatusCode());
    }
}
```
 
### Example B — `AuthControllerTest` (happy path, with real auth token)
 
```java
@Test
void login_returnsOk_whenCredentialsValid() {
 
    // ARRANGE
    LoginRequest request = new LoginRequest();
    request.setEmail("john@example.com");
    request.setPassword("Password@1");
 
    // Build a real authentication token (simulates Spring Security success)
    Authentication auth = new UsernamePasswordAuthenticationToken(
            "john@example.com", "x",
            List.of(new SimpleGrantedAuthority("ROLE_ADMIN")));
    User user = User.builder().id(10L).name("John")
            .email("john@example.com").role(Role.ADMIN).build();
 
    // Stub authenticationManager to return the token (any argument matches)
    when(authenticationManager.authenticate(any())).thenReturn(auth);
    // Stub authService to return the fake user
    when(authService.getCurrentUser("john@example.com")).thenReturn(user);
    // Stub session creation
    when(httpServletRequest.getSession(true)).thenReturn(httpSession);
 
    // ACT
    ResponseEntity<ApiResponse<AuthResponse>> response =
            authController.login(request, httpServletRequest);
 
    // ASSERT — status AND body message
    assertEquals(HttpStatus.OK, response.getStatusCode());
    assertEquals("Login successful", response.getBody().getMessage());
}
```
 
### Example C — `ProductControllerTest` (verify delegation)
 
```java
@Test
void getAllProducts_usesSearch_whenKeywordPresent() {
 
    // ARRANGE — stub search to return one product
    when(productService.searchProducts("milk"))
            .thenReturn(List.of(Product.builder().id(1L).name("Milk").build()));
 
    // ACT
    ResponseEntity<ApiResponse<?>> response = productController.getAllProducts("milk");
 
    // ASSERT status
    assertEquals(HttpStatus.OK, response.getStatusCode());
 
    // VERIFY the controller actually delegated to the right method

}
```

## 14. Summary Cheat-Sheet
 
| Annotation / Method | Where Declared | What It Does |
|---|---|---|
| `@ExtendWith(MockitoExtension.class)` | Test class | Plugs Mockito into JUnit 5 |
| `@Mock` | Test field | Creates a fake dependency |
| `@InjectMocks` | Test field | Creates the real class and wires mocks into it |
| `@Test` | Test method | Marks the method as a test case |
| `when(mock.method(args)).thenReturn(value)` | Inside `@Test` | Programs a mock to return a value |
| `when(mock.method(args)).thenThrow(ex)` | Inside `@Test` | Programs a mock to throw an exception |
| `mock(SomeClass.class)` | Inside `@Test` | Creates an inline mock (no field annotation needed) |
| `any()` / `anyLong()` / `anyString()` | Inside `when()` | Matches any argument of any/specific type |
| `assertEquals(expected, actual)` | Inside `@Test` | Asserts two values are equal |
| `verify(mock).method(args)` | Inside `@Test` | Asserts a mock method was called exactly once |
| `verify(mock, never()).method(args)` | Inside `@Test` | Asserts a mock method was never called |
 
### The Arrange–Act–Assert (AAA) pattern
 
Every test in this project follows:
 
```
ARRANGE  →  set up test data and stubs
ACT      →  call the controller method directly
ASSERT   →  check the ResponseEntity status/body and/or verify mock interactions
```
